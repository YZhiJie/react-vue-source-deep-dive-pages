# 漫画 · 第 1 话 架构总览：餐厅后厨流水线

> 对应正文：[第 1 章 架构总览](../../docs/react/01-architecture-overview.md) ｜ 原画：[01-architecture-overview.svg](./01-architecture-overview.svg)

## 登场角色

- **阿R**：React 餐厅的服务员兼主厨，蓝色小机器人，胸口的「R」是它的骄傲。
- **阿V**：隔壁 Vue 绿餐厅的主厨兼老板娘，绿发少女，头顶别着 Vue 同款 V 字发饰。
- **码叔**：猫头鹰教授，每话结尾出来划重点。

## 剧情梗概

阿V 饿了，走进阿R 的餐厅点了一份「计数器：数字从 0 变 1」。阿R 带我们参观后厨——原来一份「更新」要经过 **接单（调度）→ 备菜（render）→ 上桌（commit）** 三道流水线，才能变成用户看到的界面。

## 分格解读

### 第 1 格 · 点单即更新

用户改了 state（阿V 点单），React 收到的只是一张「订单」，不会立刻做菜。订单先进**调度台**按优先级排队——这正是第 3 话 Scheduler 与 Lane 的伏笔：不是先到先做，而是急单（输入、点击）插队，慢单（转场动画）靠后。

### 第 2 格 · 后厨 render 可中断

render 阶段是「备菜」：把界面长什么样**算出来**，产出的是内存里的一棵新 Fiber 树，一行真实 DOM 都不碰。因为只是纯计算，所以**可以随时放下手里的活**去接更急的单——这是并发渲染的根基（第 4 话详解 beginWork/completeWork）。

### 第 3 格 · 上桌 commit 一气呵成

真正的 DOM 增删改全部发生在 commit 阶段，它**同步、不可打断**——半盘菜端上桌再撤回去，客人会掀桌子的。三工位连成流水线，核心公式挂在墙上：**UI = f(state)**。数据是自变量，界面是因变量，React 负责把函数跑一遍。

## 码叔划重点

1. React 是三段流水线：调度接单 → render 备菜 → commit 上桌。
2. render 纯计算可中断，commit 动真格不可打断——「可重来的计算」与「不可撤销的副作用」严格分离。
3. Pull 式更新：React 被触发后**自己拉**最新 state 重算子树；隔壁 Vue 是 Push 式，终章对决见。

## 自测一题

**问：** 为什么 render 阶段必须保持「纯」，一行 DOM 都不能碰？

**答：** 因为 render 必须可中断、可丢弃、可重来。如果它中途改了真实 DOM，被打断后重跑就会产生「半更新的界面」；只有把它限制为纯计算，React 才敢随时按下暂停键。真正动 DOM 的脏活全部推迟到同步不可打断的 commit 阶段。

## 进阶追问

**问：** 这一话的流水线里，「调度」为什么能决定谁先做菜？优先级信息存在哪里？

**答：** React 19 用 Lane 模型表达优先级：每次更新带一个二进制位（lane），根节点记录「还有哪些 lane 没做完」，`ensureRootIsScheduled` 每次都重新选出当前最急的 lane 开一轮 render。低优先级 render 进行中来了急单，旧 render 可以丢弃、用新 lane 重来。这正是第 3 话「急诊分诊台」的内容，建议看完 EP.03 再回头读本格，会有串联感。
